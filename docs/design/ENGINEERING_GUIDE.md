# 개발 규칙 (코딩 규칙 · Git · PR · 리뷰 · 완료 정의)

상태: **제안**. `AGENTS.md` §7·§9·§10과 `TASKS.md` §0을 사람이 쓰기 좋게 풀었다. 충돌하면 AGENTS.md가 이긴다. 명령어(설치·실행 등)는 T-00이 끝나야 정해지므로 `RUNBOOK.md`의 `[확인 필요]` 칸을 채운다.

## 1. 반드시 지킬 것 (요약)

1. 확정 전에는 일정·알림을 만들지 않는다.
2. AI가 날짜 값을 만들게 하지 않는다. 날짜는 서버 규칙이 계산한다.
3. 시각을 못 찾으면 "시각 미확인". 임의 시각 금지. 연도를 추정했으면 표시.
4. 로그에 공고 본문·비밀값·푸시 주소·비밀번호 금지.
5. 범위 밖 기능 금지. 10/16 이후 새 기능 금지(버그 수정만).
6. 승인 전 결정(D-29·30·31·38·40)에 기대는 코드는 `[승인 의존: D-xx]` 주석.
7. 문서에 빈 곳이 있으면 **추측하지 말고** 질문(`DECISION_LOG.md` §4)을 남기고 멈춘다.

## 2. 코딩 규칙

### TypeScript (apps/web)
- `strict: true`. `any` 금지(`as any`, `<any>` 포함). 모르면 `unknown`을 좁힌다.
- 서버 전용 코드는 `src/server/` 아래. 클라이언트 번들에 들어가면 안 되는 모듈은 `import "server-only"`.
- 현재 시각은 `clock`에서만. `Date.now()`, `new Date()`(무인자) 직접 호출 금지.
- 환경값은 `src/lib/env.ts` 한 곳에서 읽고 검증한다. 그 밖에서 `process.env`를 읽지 않는다.
- 한국어 문구는 `messages.ts`에만. 컴포넌트에 문장을 직접 쓰지 않는다.
- 날짜·시각 표시는 `DeadlineLabel` / `formatKst`만. 화면에서 날짜 계산을 새로 하지 않는다.
- 오류는 `{code, message}` 형식으로만 던지고/받는다. 예외 객체를 그대로 응답에 넣지 않는다.
- 사용자 입력은 서버에서 반드시 검증한다(스키마 검증 라이브러리, 예: zod).

### Python (services/ai)
- 모든 함수에 타입 힌트. `mypy --strict` 또는 `pyright` 통과.
- 현재 시각은 `clock.py`에서만. `datetime.now()`, `utcnow()` 금지.
- 환경값은 `env.py` 한 곳.
- 날짜 정리(`normalize`)는 **순수 함수**: 시계·네트워크·DB·파일을 만지지 않는다.
- 외부 호출(Gemini)은 `ExtractionClient` 인터페이스 뒤. 모의 구현으로 시험한다.
- 예외를 삼키지 않는다. 처리 못 하면 `fail_extraction_job`을 부른다.

### SQL (supabase)
- **이미 적용된 마이그레이션은 고치지 않는다.** 바꿀 일이 있으면 새 번호 파일(`0004_*.sql`)을 추가하고 이유를 PR에 쓴다.
- 새 함수는 `p_now`를 인자로 받고, 마지막에 권한 회수/부여 블록을 적용한다(`service_role`만 실행).
- 새 표/함수에는 시험을 같이 추가한다. 기존 시험은 계속 통과해야 한다 (`run_local_check.sh` → `ALL PASSED`).
- 여러 표를 바꾸면 함수 한 번. 서비스 코드에서 표를 나눠 쓰지 않는다.

### 공통
- 이름은 의미가 드러나게. 약어를 새로 만들지 않는다(용어는 `GLOSSARY.md`).
- 주석은 "왜"를 쓴다. 규칙 번호(`규칙 9`)·결정 번호(`D-38`)·AC 번호를 적는다.
- 함수는 한 가지 일. 길어지면 나눈다.
- 중복 코드는 세 번째에서 합친다(너무 일찍 추상화하지 않는다).

## 3. Git 규칙

| 항목 | 규칙 |
|---|---|
| 브랜치 이름 | `t-01-date-normalize`, `t-04-posting-api` (과업 번호 + 짧은 설명) |
| `main` | 항상 시험이 통과하는 상태. 직접 올리지 않는다 |
| 커밋 | 한 가지 변경. 제목: `T-01 FR-JOB-06 AC-JOB-04 날짜 정리: 시험표 13줄 추가` (과업·FR/AC/D 번호 + 한 줄) |
| PR | 작게(하루 안에 리뷰 가능한 크기). 제목·본문에 과업/FR/AC/D 번호. 문서와 코드는 **같은 PR** |
| 합치기 | 시험 통과 + 리뷰 승인 후. 합치기 방식은 한 가지로 통일(제안: squash) |
| 비밀 | `.env`는 커밋하지 않는다. 실수로 올렸다면 키를 즉시 폐기 (`SECURITY_PRIVACY.md` §7) |

## 4. PR 템플릿

```markdown
## 과업 / 요구사항
- 과업: T-xx
- FR: FR-...  AC: AC-...  D: D-... (승인 의존이면 표시)

## 무엇을 바꿨나 (3줄 이내)

## 어떻게 확인했나
- [ ] 시험을 먼저 썼다 (시험 이름: …)
- [ ] 전체 시험 통과 (명령: …)
- [ ] 린트·타입 검사 통과

## 점검 (해당 시 체크)
- [ ] 새 `[승인 의존]` 코드는 주석과 DECISION_LOG에 반영했다
- [ ] 로그/응답에 공고 본문·비밀값을 넣지 않았다
- [ ] 확정 전 일정·알림이 만들어지지 않는다
- [ ] 소유자 확인이 서버에서 이뤄진다 (남의 자료 = 404)
- [ ] 쓰기가 멱등이다 / 화면 버튼이 누르자마자 비활성화된다
- [ ] 문구는 messages.ts, 날짜 표시는 DeadlineLabel
- [ ] 문서(해당 파일)를 같은 PR에서 고쳤다
- [ ] 범위 밖 기능이 없다

## 문서와 다른 점 / 질문 (없으면 "없음")

## 남은 위험
```
에이전트(Cursor)가 쓴 코드는 PR 본문에 "이 코드가 무엇을 하는지"를 **자기 말로 3줄** 쓴다.

## 5. 리뷰 체크리스트

리뷰어는 아래를 순서대로 본다. 하나라도 아니면 합치지 않는다.

1. 범위: 과업·FR에 없는 변경이 섞였나? (AGENTS.md §10)
2. 시험: 시험이 먼저 있나? 이름에 AC 번호가 있나? 시험이 일부러 깨뜨린 코드를 잡나?
3. 약속: 확정 전 일정 생성 / AI가 날짜 생성 / 임의 시각 / 연도 추정 표시 누락이 없나?
4. 보안: 소유자 확인, 본문 로그, 키, 입력 검증, XSS(`dangerouslySetInnerHTML`)
5. 원자성: 표 2개 이상을 바꾸는 쓰기가 DB 함수 한 번인가?
6. 시계·환경·문구: `Date.now()` 직접 호출, `process.env` 직접 읽기, 컴포넌트 안 한국어 문장이 없나?
7. UX: 로딩/빈/오류/오프라인/중복 제출 상태가 있나? 비활성 버튼에 이유가 있나? (UX 7장 점검표)
8. 이해: PR 작성자가 코드를 설명할 수 있나?
9. 문서: 같은 PR에서 문서를 고쳤나? 번호(FR/AC/D/화면/API)가 맞나?

## 6. 완료 정의 (Definition of Done)

과업/PR이 "끝"이려면 모두 참이어야 한다.
- [ ] 완료 조건(`TASKS.md` 해당 과업)을 전부 통과했다.
- [ ] 시험이 먼저 쓰였고 통과한다. 이름에 AC/X/ERD 번호가 있다.
- [ ] 전체 시험이 통과한다 (기존 시험 포함).
- [ ] 린트·타입 검사 통과, `any` 없음.
- [ ] 리뷰 승인.
- [ ] `[승인 의존]` 표시와 `DECISION_LOG.md` 목록이 일치한다.
- [ ] 문서가 코드와 일치한다 (`REQUIREMENTS_TRACE`, `API_SPEC`, `UI_SPEC` 등).
- [ ] 로그 점검: 본문·비밀 없음.
- [ ] `TASKS.md` 체크박스를 `[x]`로 바꾸고 PR에 바뀐 파일과 남은 위험을 적었다.

## 7. 에이전트(Cursor) 사용 규칙

1. 한 번에 **과업 하나**. `TASKS.md`의 해당 과업 전체와 `AGENTS.md`를 프롬프트에 포함한다.
2. "시험부터 쓰고, 통과하는 구현을 쓰라"고 명시한다.
3. 문서에 없는 것은 **추측하지 말고 질문 기록에 남기게** 한다.
4. 결과를 읽고 이해한 뒤 PR에 올린다. 이해 안 되는 부분은 지우거나 다시 시킨다.
5. 에이전트가 만든 마이그레이션은 특히 꼼꼼히 본다(되돌릴 수 없다).
6. 에이전트가 "이미 있는 파일"을 덮어쓰는지 diff로 확인한다 (예: 0001 수정 금지).

## 8. 정합성 점검 (문서 ↔ 코드)

PR마다, 그리고 제출 전에 한다.
- FR/AC/D 번호가 `REQUIREMENTS_TRACE.md`에 있는 번호인가.
- 화면 번호(S-xx), API 번호(API-nn), 함수 이름이 문서와 코드가 같은가.
- `grep -r "승인 의존"` 결과 = `DECISION_LOG.md` §1의 "코드에서 기대는 곳".
- `grep -rn "TODO\|FIXME"` 는 질문 기록의 번호와 연결되어 있거나 없다.
